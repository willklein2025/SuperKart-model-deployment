# SuperKart Sales Prediction and Deployment

Predicts `Product_Store_Sales_Total` (revenue from one product in one store) for SuperKart, a retail chain, and packages the model as a Streamlit app that can be deployed to a Hugging Face Space with Docker.

## Files

| File | Purpose |
|---|---|
| `Full_Code_SuperKart_Model_Deployment_Notebook.ipynb` | EDA, preprocessing, model building and tuning, model export, deployment files, business insights (executed, outputs included) |
| `SuperKart.csv` | Data: 8,763 rows, 12 columns (product and store attributes, plus the sales total) |
| `backend_files/` | Generated by the notebook: `app.py`, `requirements.txt`, `Dockerfile`, `superkart_sales_model.joblib` |

## Running it

```bash
pip install numpy==2.0.2 pandas==2.2.2 scikit-learn==1.6.1 matplotlib==3.10.0 seaborn==0.13.2 joblib==1.4.2 xgboost==2.1.4 huggingface_hub==0.34.0 jupyter
jupyter notebook
```

Keep `SuperKart.csv` next to the notebook (or set `SUPERKART_CSV`). Running everything takes roughly 10 minutes (the pair plot and the two hyperparameter searches are the slow parts).

Run the Streamlit app locally from the `backend_files` folder:

```bash
pip install -r requirements.txt
streamlit run app.py
```

### Deploying to Hugging Face

Upload is **off by default** (`UPLOAD_TO_HF = False`). To deploy, create a Docker Space (the notebook defaults to `TXSailor/SuperKart`; override with `HF_REPO_ID`), set `UPLOAD_TO_HF = True`, and provide a write token in the `HF_TOKEN` environment variable or at the prompt. Do not paste tokens into the notebook.

> **Security:** the original notebook had a live Hugging Face token written in plain text. Revoke it at https://huggingface.co/settings/tokens and create a new one. Anyone who has seen the notebook or its Space history could use the old one.

## Approach

1. **EDA** on products and stores, with data cleaning: the "reg" sugar label is merged into "Regular".
2. **Features:** product code prefix (FD / DR / NC) from `Product_Id`, store age (2025 minus year established), and a Perishables / Non Perishables grouping of the 16 product types. `Product_Id`, `Product_Type`, `Store_Id` and `Store_Establishment_Year` are dropped.
3. **Models:** Gradient Boosting and XGBoost regressors, untuned and tuned (`RandomizedSearchCV`, 30 draws, 3-fold CV, R-squared scoring), 70/30 train/test split.
4. **Selection** by 5-fold cross-validated R-squared on the training set only; the test set is a final check.
5. **Export** the selected pipeline with joblib and generate the Streamlit app, requirements and Dockerfile.

## Changes from the original notebook

**Bugs that changed the results**
- **Numeric features were dropped.** The column transformer listed only the categorical columns and used the default `remainder="drop"`, so weight, MRP, display area and store age never reached any model. The numeric ones are the strongest predictors (MRP correlation with sales about 0.79, weight about 0.74). Test R-squared rises from about **0.67 to about 0.92** with the fix.
- **Gradient boosting tuning never ran.** `scoring=r2_score` (a function) is not a valid scorer; with warnings suppressed, every fit failed quietly and the "tuned" model was the first parameter combination. Now `scoring="r2"`.
- **Wrong charts.** The OUT002, OUT003 and OUT004 product-type charts plotted OUT001's values. They now use each store's own data, in one loop.
- **Model chosen on the test set.** The "best model" was picked by looking at test scores. It is now picked by cross-validation.

**Conclusions corrected**
- Category and store comparisons used **total** sales, which mostly reflect how many products each group has. OUT004 is "top" only because it has 4,676 of the 8,763 rows, and Fruits and Vegetables / Snack Foods lead because they have the most products. Sales per product are about the same across product types (roughly 3,400-3,700) and are highest at OUT003 (about 4,950) and lowest at OUT002 (about 1,760). The insights and recommendations were rewritten around this.
- The "price elasticity" section plotted average price against total sales; it is now average price against sales per product, and described as an association, not elasticity.
- Several EDA remarks were wrong (e.g. "average store sales just under 4000": it is about 3,460; statements about "most stores" when there are only four).

**Deployment and housekeeping**
- Removed the hard-coded Hugging Face token; upload is opt-in.
- Colab-only Drive mount and paths removed; data is read from a local file.
- `requirements.txt` slimmed (Flask, gunicorn, Werkzeug, uvicorn, seaborn, requests and a duplicate `joblib` removed). The Dockerfile uses Python 3.11, installs dependencies before copying code (better layer caching), and no longer disables Streamlit's XSRF protection.
- App: removed the unused imports, bounded the display-area input to 0-1, dropped the unexplained `$` sign, clarified the product-code label.
- Model file renamed `superkart_sales_model.joblib` (it is whichever model is selected, not necessarily gradient boosting).
- Saved outputs regenerated; the extra scatter charts use average sales per product.

## Limitations

- **Only four stores** are in the data, and store size, city tier, type and age identify each one. The model effectively learns four stores' behaviour; do not rely on it for a new store.
- Rows are product-store totals with no dates, so this is a cross-sectional estimate of sales, not a quarter-ahead time-series forecast, despite the business framing.
- Currency and period of the sales figures are not stated in the data.
- Pinned versions (scikit-learn 1.6.1 etc.) must match between training and the app; the saved model is only guaranteed to load with the same scikit-learn version it was trained with.
- This run used newer library versions than the pinned ones (Python 3.13, scikit-learn 1.9, xgboost 3.4), so numbers may differ slightly when you rerun with the pins.
